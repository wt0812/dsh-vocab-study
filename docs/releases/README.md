# Release 正文（GitHub Releases 用）

这里的每个文件就是对应 tag 的 **GitHub Release 正文**。改完用 `gh release edit` 覆盖上去。

**为什么要单独存一份**：Release 正文**仓库里原本没有源文件** —— 当初是直接打命令行写进去的，
结果 `v0.2.0`~`v0.2.5` 五个版本的 Release **漏了没建**，`v0.2.6` 那份结构也写偏了。
存成文件之后，改版正文可以 review、可以 diff，不会再漏。

## 格式（跟市场弹窗实际渲染的样子对齐）

```markdown
（摘要段：一句话说清这版干了什么。裸段落，不要 # 标题）

> **重要变更**：有没有破坏性改动、要不要手工迁移。没有就明说"无"。

## 新功能

- …

## 修复

- …

## 其他改动

- …
```

### 为什么是长这样

市场那个「更新内容」弹窗（`dshmarket`）会把 Release 正文过一遍**白名单渲染**
（`renderMarkdown`）：先剥掉 HTML，只留**标题 / 引用 / 代码块 / 圆点 / 粗体 /
行内代码 / https 链接 / 白名单图片**。表格和 `---` 分隔线会被丢掉。

实测那份渲染得最完整的正文，结构就是上面这样：**摘要裸段落 + `>` 引用块 + 小节标题**。
完整的数据来源与降级链记录在仓库根目录 `SHIPPING.md` 的《更新说明》一节。

### 四条硬规矩

1. **首行不要写 `## 一句话`** —— 那会渲染成一个不该有的特大标题。摘要段就写裸段落。
2. **纯修复版不要硬编 `## 新功能`**。`v0.2.1` / `v0.2.4` / `v0.2.5` 就没有，空着比编一个"无"更干净。
3. **版本号跳号要明说**（我们从 0.2.1 直接到 0.2.3，npm 上没有 0.2.2）。
4. **正文里不许出现尖括号** —— 连行内代码包着的也不行。

   为什么第 4 条特别反直觉：上游 `renderMarkdown` 是**先剥 HTML、再按 Markdown 渲染**，
   它不看结构。所以 `` `clip<t:cut…>` `` 这种"只是引用了坏数据样本"的写法，
   渲染出来会把这个词连同里面的字一起吃掉。
   2026-10-19 写 v0.2.9 时真踩到了，被 `node tools/verify-market-notes.mjs` 的格式体检抓出来。

### 发之前先体检

```sh
node tools/verify-market-notes.mjs --assume-snapshot v0.2.9 --installed 0.2.8
```

它会告诉你：市场快照里我们现在是哪一版、弹窗按判定会显示哪一档
（版本说明 / 提交记录 / npm 时间 / 未收录）、正文能不能过白名单。
判定逻辑为什么有时候不给看正文，记在 `SHIPPING.md` 的《更新说明》一节。

## 改完怎么发

```sh
gh release edit v0.2.6 --repo wt0812/dsh-vocab-study \
  --title "v0.2.6 —— 修「底部进度停在上一轮」" \
  --notes-file docs/releases/v0.2.6.md
```

## 注意：这只影响"合并之后"

市场弹窗的更新说明数据来自
[`dsh-plugin-updates`](https://www.npmjs.com/package/dsh-plugin-updates) 这个 npm 包里的
`updates.json`，而它是**从市场主分支的目录条目生成的**。

**我们的 PR 还没合并 → 数据里还没有我们 → 弹窗里看不到任何更新说明。**
所以这里写得多好，**都要等 PR 合并、次日 `updates.json` 重生成之后才体现**。
