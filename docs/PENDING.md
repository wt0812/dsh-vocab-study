## 3. 构建脚本的一个脆弱点：括号深度扫描不认字符串

**现象（2026-10-19 真实踩到）**

`tools/build.py` / `tools/build-plugin.py` 的 `top_level_decls()` 用「逐行累加 `{` `}` 净数」
判断当前是不是顶层。如果**数据文件里的字符串**含花括号（哪怕完全合法），
深度就会漂移，后面声明的常量会被当成「源码里不存在」：

```
[vocab-study] CORE_EXPORTS 里登记了源码中不存在的符号：ETD.ETYM_COVERAGE
```

**当时的处理**：改生成器（`tools/make-etym.py` 的 `FORBIDDEN_RE`），
让数据文本里**永远不出现** `{ } < > | = [ ]`，并把不合规条目整条丢掉。
这是对的（数据本来也不该带模板残留），但只是**绕开**，不是修好。

**要做的**：把 `top_level_decls()` 改成按字符扫描、跳过 `'…'` `"…"` `` `…` `` 字符串与
`//` `/* */` 注释，再数花括号。改完请用一份含花括号字符串的假数据验证一次。

**2026-10-20 进展（部分修好，但没敢全修）**

- ✅ 悬空命名空间前缀检查已经这么做过了：`mask_strings_and_comments()` 把字符串/注释
  换成等长空格再扫。真实收益：例句 `A.I. won't reach singularity.` 曾让构建报
  "残留命名空间 A.I" 而失败，现已不误报。
- ❌ 但同一个屏蔽**不能**直接套给 `top_level_decls()`：全局屏蔽会把**正则字面量里的引号**
  （如 `/['’]/`）当成字符串开头，一路吞到下一个引号，把后面大段源码抹成空格，
  于是真声明被判成"不存在"，报 `CORE_EXPORTS 里登记了源码中不存在的符号：L.seedFor …`。
  这比原来的问题更危险（原问题只在数据含花括号时才炸），已回滚。
- 要彻底修，`top_level_decls()` 需要一个**认得正则字面量**的词法器（按上一个有效 token
  判断 `/` 是除号还是正则）。在那之前，数据文件里请避免在字符串中写 `{` `}` ——
  生成器那边已经在 `core/*-data.mjs` 头部注明了。
